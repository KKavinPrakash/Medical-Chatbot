# Vectorless RAG Chatbot - Reverse Engineering Documentation

## Executive Summary

This document details the architectural configuration and evaluation of the **Vectorless** offshoot of the Medical Chatbot project. It has been deliberately engineered to sidestep expensive dense-vector embedding dependencies while maintaining absolute Free-Tier compliance using statistical probability (BM25).

## 2. Page Index Ingestion (`create_memory_vectorless.py`)

Unlike the traditional FAISS implementation, this pipeline explicitly does **not** chop the texts into arbitrary limits (e.g., 500-char chunks). 

**Process Flow:**
1. **`PyPDFLoader` Extraction**: Reads PDFs structurally. It organically separates physical pages into single, standalone `Document` nodes with `metadata={"page": n}`.
2. **Keyword Generation**: The `BM25Retriever` parses every node, calculating Term Frequencies & Inverse Document Frequencies mapping for every page without utilizing transformer models.
3. **Serialization**: The entire graph mapping is saved directly to `vectorstore/bm25_index.pkl` via the standard Python `pickle` library for high-speed local loading.

---

## 3. Retrieval & Memory Strategy (`medibot_vectorless.py`)

### 3.1 Context Serialization
When the Streamlit Chatbot initializes, it pulls the `pickle` indexed binary into RAM. Without having to instantiate a 400MB language model for Embeddings, initial load time is drastically reduced.

### 3.2 Conversational Awareness
The system maintains conversation momentum through a multi-tiered LangChain proxy:
1. **Query Transformation**: User inputs are fed into the Groq LLM alongside `st.session_state` chat history. The LLM constructs a "standalone query".
2. **Node Interception**: The newly condensed query hits the BM25 statistical matrix to fetch the **Top 3** most exact-match physical pages.
3. **Source Highlighting**: Since the underlying `PyPDFLoader` metadata (the physical Page ID) is never severed by a TextSplitter, the system surfaces exact UI citations: `Sources: Document Pages X, Y`.

---

## 4. Drawbacks vs. Advantages

### Advantages over Existing FAISS
* **Zero Cost**: Bypasses any dependency on HuggingFace token limits or paid API endpoints.
* **Exact Keyword Retrieval**: Finds heavy medical compound names faster than semantic similarity networks.
* **Structural Context**: Retains perfect bounds of physical pages (does not arbitrarily break a chemical definition in half because the char limit was reached).
* **Conversational Memory**: Follow-up questions intelligently reference prior questions.

### Drawbacks
* **Literal Matching**: While BM25 implies a level of intelligence via Inverse Document frequencies, it struggles if the user doesn't use the exact synonym of a disease vs what was formulated in the text.
* **Pickle Security**: Un-pickling local data (`.pkl`) executes objects into local memory and carries implicit security risks if the index was generated by an unverified third party.
